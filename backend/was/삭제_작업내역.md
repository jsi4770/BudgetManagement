## 1. 넘기는 것 / 남아 있는 것

경계를 잘못 읽으면 남아 있는 코드를 다시 만들게 된다. 아래가 그 경계다.

### ① 이상치 탐지 (Z-score)

| | |
|---|---|
| **만들 것** | Z-score·평균·증가율 계산, 표본 수집, ANL-03 엔드포인트 |
| **남아 있는 것** | `TransactionRepository.sumExpensesByCategory` (구간별·카테고리별 지출 합계 쿼리) + 그 projection `CategoryAmountSum` |
| **읽을 곳** | 명세 ANL-03 · `서버_내부_처리.md` 3장 · ERD 6장 · 시연 6-1/6-3 |

원래 `SpendingSampler`(`domain.analysis`)가 그 쿼리를 감싸 ANL-03과 넛지 판정이 공유하는
유일한 조회 경로였다. 호출자가 전부 사라져 같이 걷어냈으니 **다시 만들 때 공용 진입점을
하나 둘 것** — ANL-03 화면의 "평소 평균"과 넛지 카드의 "평소 이맘때 평균"이 어긋나지 않게
하려면 집계 경로가 하나여야 한다(`서버_내부_처리.md` 3장: *"같은 계산 함수 사용"*).
`TransactionAnalysisQueryTest` 가 그 쿼리를 계속 검증하고 있으니 거기서부터 시작하면 된다.

Z 계산은 **순수 함수로 분리**할 것. ERD 6장이 정한 세부:

- 표본 표준편차(n−1)
- 표준편차 0 → Z는 `null` ("판정 생략 ②")
- 표본이 전부 0 → 증가율만 `null`
- **Z와 증가율은 반올림한 정수 평균에서 계산**한다 — 그 정수가 `NUDGE.AVG_AMOUNT`로 저장되고
  화면에도 나가므로, 별도의 정밀 평균을 쓰면 저장값과 화면값이 어긋난다
- 이상 판정 임계: Z ≥ 2 **그리고** 차이 ≥ 30,000원
- **데이터 충분성 판단과 월세 제외는 이 함수의 일이 아니다** — 가입일을 알아야 하고, 월세 제외
  여부는 호출자마다 다르다

월세(`RentCategory.ID` = 5) 제외 여부가 호출자마다 다르다는 표는 `RentCategory` 클래스 주석에
남아 있다. 요약: 넛지·ANL-02·ANL-03 `WEEK` 에서는 제외, ANL-01과 ANL-03 `MONTH` 의 **총액에는
포함하되 평균·증가율은 `null`**.

ANL-03의 `WEEK`/`MONTH` 차이(분석 범위·표본 범위·표본 수·월세 처리·이상 플래그)는 원래
`AnalysisPeriod` 라는 enum이 **전부** 들고 있었다. 서비스에 `if (period == WEEK)` 를 뿌리면 이
엔드포인트는 조용히 반만 바뀐다 — enum으로 되살릴 것을 권한다.

### ② 넛지 도메인

| | |
|---|---|
| **만들 것** | `NUDGE` 테이블·엔티티·리포지토리, 넛지 판정(후처리 3번), NDG-01~03, AI 문구 채우기(후처리 5번) |
| **남아 있는 것** | `NudgeJudgement` 인터페이스 + 호출 지점 3곳 (`TransactionService`) + `NoOpNudgeJudgement` |
| **읽을 곳** | 명세 NDG-01~03 · ERD 6장 · `서버_내부_처리.md` 1장 순서 3·5번 · 3장 · 8장 · `AI_대체_문구.md` 1·2장 |

1차 인수인계 때는 COACH-01/03이 읽고 있어서 엔티티를 남겨 뒀지만, 코칭까지 넘어가면서
**읽는 코드가 하나도 없어져 엔티티도 걷어냈다.** 테이블을 다시 만들 때 필요한 것:

- 복합 UNIQUE `(user_id, category_id, analysis_start_date)` = "한 사용자의 한 카테고리에 한
  주당 한 장". `ANALYSIS_END_DATE` 는 판정일마다 바뀌므로 **키에 들어가지 않는다** — 그래서
  같은 주에 거래가 더 쌓이면 새 행이 아니라 그 행이 갱신된다
- upsert의 **갱신** 쪽은 ERD가 나열한 다섯 컬럼만 바꾼다(`ANALYSIS_END_DATE` ·
  `SPENDING_AMOUNT` · `AVG_AMOUNT` · `Z_SCORE` · `GROWTH_RATE`). **`status` 와 AI 문구는
  건드리지 않는다** — 닫은 카드는 닫힌 채로 남아야 하고(ERD 6장 "갱신 시 STATUS 유지"), AI
  문구는 재생성이 끝날 때까지 이전 것을 보여 준다
- `Z_SCORE` 는 NOT NULL 이므로 `null` 인 비교 결과로 카드를 만들려 하면 거부해야 한다

`NudgeJudgement` 인터페이스 javadoc에 규칙을 다 적어 뒀다. 특히:

- **판정 기간은 언제나 이번 주.** 3주 전 거래를 고쳐도 다시 판정해야 한다 — 그 거래는 직전 4주
  표본에 들어가 평균과 Z를 바꾼다. 그래서 호출자는 거래 날짜로 걸러내지 않고 무조건 부른다
- `judge(user, Category...)` 는 **구현에서 ID로 중복 제거**해야 한다 (TX-05가 수정 전·후를 둘 다
  넘기고, `null` 이 섞여 들어올 수 있다)
- 표본 조회는 카테고리 수와 무관하게 **구간 수**(이번 주 + 4주)만큼
- 판정 대상은 지출 카테고리이고 월세가 아닌 것뿐
- **"판정 생략"은 아무것도 건드리지 않는 것**이다(가입일이 표본 첫 주 월요일 이후 / 표준편차 0).
  기존 카드를 지우지도 갱신하지도 않는다. 이건 "조건 미달로 바뀜"(= `UNREAD` 카드 삭제, 반응한
  카드는 유지)과 **다르다**

NDG-01~03에서 원래 내렸던 결정들, 다시 밟지 않도록:

- **NDG-01의 `data: null`** — "오늘 카드 없음"은 200이고 `data` 가 `null` 이다. 공용
  `ApiResponse` 는 `@JsonInclude(NON_NULL)` 로 `data`/`error` 배타성을 지키느라 이걸 표현할 수
  없어서, 전용 타입(`NullableApiResponse`)을 하나 뒀었다. `ApiResponse` 쪽 애노테이션을 풀면
  **모든 에러 응답에 `data: null` 이 끼므로** 그러지 말 것. 명세에서 `data: null` 을 쓰는 곳은
  NDG-01 하나다
- **노출 조건 세 개는 쿼리에** — 이번 주 월요일(`analysisStartDate` 동등 비교) · `UNREAD` 만 ·
  `updatedAt` 최신순
- **NDG-02에는 노출 조건이 없다** — 지난주 카드도, 닫은 카드도 열린다. 소유권만 쿼리에
  (`findByIdAndUserId`)
- **제목은 저장하지 않는다**(ERD 6장) — 카테고리명으로 `"%s 지출이 평소보다 늘었어요"` 를 조합.
  저장하면 카테고리 이름이 바뀔 때 과거 카드만 옛 이름으로 남는다
- **`zScore` 는 저장하되 응답에 넣지 않는다**(명세 NDG-01)
- **NDG-03은 `NudgeStatus` 가 아니라 "반응" 전용 타입을 받을 것** — 클라이언트가 `UNREAD` 를
  보내 닫은 카드를 되살리면 "닫은 넛지는 재노출되지 않음"이 깨진다. 좁은 타입이면 `"UNREAD"` 와
  `"FOO"` 가 **같은** 400을 받는다(검증기를 따로 만들면 에러 모양이 갈린다)
- 같은 상태를 다시 보내는 것은 200 (명세에 에러가 없고, 실패시키면 프론트 재시도가 막힌다)

후처리 5번(AI 문구)은 `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` 다. 함정 셋:

1. **`@Transactional` 은 `REQUIRES_NEW` 여야 한다.** 기본 전파로 두면 Spring이 **시작 시점에**
   빈을 거부한다 — 끝난 트랜잭션에 참여한 AFTER_COMMIT 리스너는 쓰기를 조용히 버리게 되므로
2. **이벤트에는 엔티티가 아니라 id를 담을 것.** 리스너는 컨텍스트가 닫힌 뒤 다른 스레드에서
   돈다. id로 다시 읽으면 "그 사이에 카드가 지워진" 경우도 공짜로 처리된다
3. **문구의 `{days}` 는 저장된 분석 기간에서** 가져올 것(`today` 가 아니라). 비동기 실행이
   자정을 넘기면 문구가 판정한 기간을 설명해야 한다

문구 생성 포트는 **절대 예외를 던지지 않는 계약**으로 만들 것 — 실패 시 `AI_대체_문구.md`
1·2장 템플릿으로 떨어지는 것이 명세이고, 그 폴백이 구현 **안에** 있으면 호출자에 `try/catch` 가
없다. (TX-07의 포트와 반대 선택이다. 그쪽은 실패가 클라이언트에 503으로 나가야 해서 던진다.)

### ③ 코칭 (COACH-01~04)

| | |
|---|---|
| **만들 것** | `COACHING` · `COACHING_MESSAGE` 테이블, COACH-01~04, 첫 메시지·답변 생성 포트, 룰 기반 목표 제안 |
| **남아 있는 것** | 없음 (패키지 전체가 사라졌다) |
| **읽을 곳** | 명세 COACH-01~04 · ERD 7·8장 · `서버_내부_처리.md` 6장 · 8장 · `AI_대체_문구.md` 3·4·5장 |

구조상 꼭 지켜야 하는 것:

- **`COACHING` 에 `NUDGE` 로 가는 FK를 두지 말 것**(ERD 7장). COACH-01의 `nudgeId` 는 첫 AI
  메시지의 컨텍스트로만 쓰고 그 넛지를 `COACHING_STARTED` 로 바꾼다 — 아무것도 저장하지
  않는다. 저장하면 아무도 하지 않은 제안이 COACH-02에 떠오른다
- **COACH-01 안의 순서가 규칙이다**: 넛지를 **먼저** 조회하고(404 가 날 수 있는 유일한 단계),
  **그 다음** 이전 `IN_PROGRESS` 세션을 취소한다. 뒤집으면 실패한 요청이 살아 있는 대화를
  죽이는 경로가 된다
- 이전 세션 취소는 `List` 로 읽을 것. "사용자당 `IN_PROGRESS` 하나"는 DB 제약이 아니라 코드가
  지키는 불변식이라(ERD 7장에 unique index 없음) 두 탭이 경쟁하면 두 행이 남을 수 있고,
  `Top1` 쿼리면 한 번에 하나씩만 치운다
- **진행 중 챌린지 확인은 COACH-01의 일이 아니다** — "진행 중 챌린지가 있어도 대화 시작 가능,
  확정만 차단"(명세 COACH-01 · ERD 7장). 2026-11-09에 여기 409 게이트를 넣었다가 명세 위반으로
  같은 날 되돌린 기록이 있다. **COACH-04만 막는다**
- COACH-01의 본문은 **선택**이다(`nudgeId` 하나뿐). 빈 본문이 400이 되지 않게 할 것
- 없는/남의 `nudgeId` 는 **404** (명세 COACH-01에 에러 목록이 없지만 0장 5) 규칙. 조용히 일반
  인사로 내려가면 프론트 버그가 "AI가 내 맥락을 잊었다"로 둔갑한다)
- **COACH-02는 종료된 세션도 읽는다** — 상태로 걸러내지 않는다. 409 `COACHING_ALREADY_ENDED` 는
  "종료된 코칭에 **요청**"(`서버_내부_처리.md` 6장), 즉 COACH-03/04의 **쓰기** 규칙이다
- **코칭 목록 API는 없다**(명세 COACH-02) — 목록 쿼리를 만들지 말 것. 프론트는 항상 id를 들고 온다
- 응답 키는 `id` 가 아니라 **`coachingId`** 이고 `updatedAt` 은 내보내지 않는다. COACH-01과
  COACH-02가 **같은 형식**이라 응답 타입을 공유하는 것이 맞다
- `COACHING_MESSAGE` 정렬은 **`(createdAt, id)`** — COACH-03이 사용자 메시지와 AI 답변을 한
  요청에서 저장하고 `CREATED_AT` 이 초 단위라, 동률이면 답이 질문보다 먼저 복원된다
- 사용자 메시지를 **포트 호출 전에** 저장할 것(ERD 8장: 모델에 넘기는 대화가 답할 질문으로
  끝나야 한다). 그리고 이력은 메모리에서 이어 붙이지 말고 리포지토리로 다시 읽을 것 — 순서의
  정의가 한 곳이어야 한다

**COACH-03은 AI가 죽어도 200이다.** 명세 0장 4) 각주와 `서버_내부_처리.md` 8장이 "에러 대신
대체 메시지로 200"을 요구한다. 두 가지가 같이 따라온다:

- 포트 호출만 `try` 안에 넣고 **`RuntimeException` 을 잡을 것.** `BusinessException` 만 잡으면
  매핑되지 않은 예외 하나가 "절대 에러 안 냄" 규칙을 500으로 바꾼다
- `isFallback` 은 **포트의 반환값에 두지 말 것.** 포트가 돌아온 것 자체가 성공이고, 플래그는
  답을 만든 쪽(서비스)이 안다 — 그래야 어댑터가 틀리게 설정할 수 없다. 이 값은 **저장하지도
  않는다**(ERD 8장), 그래서 COACH-02 응답에는 그 키가 없고 COACH-03 응답에만 있다
- 응답의 `proposal` 은 **이번 턴에 제안한 것만**이다(명세 COACH-03). 저장된 걸 읽으면 세 턴 전
  제안이 매 턴 되살아난다. 저장된 것을 복원하는 건 COACH-02의 일이다
- 제안을 저장하기 **전에 검증**하고, 잘못된 제안은 버리되 **메시지는 그대로 보낼 것.** 저장된
  제안은 COACH-04가 챌린지로 바꾸는 것이라 없는 카테고리·수입 카테고리·ERD 7장 check 위반이
  들어가면 안 된다
- 제안은 **하나만 유지**한다. `goalType` 을 바꾸면 반대쪽 목표 컬럼을 **비울 것**(ERD 7장) —
  안 비우면 새 횟수 목표 옆에 옛 금액이 남는다

**룰 기반 목표 제안**(`AI_대체_문구.md` 5장)이 Gemini 없이도 "넛지 → 코칭 → 챌린지" 흐름을
굴러가게 하던 장치다. DB를 읽으므로(직전 4주 지출 · 예산의 소비 관리 목표 · 이번 주 넛지)
`domain.ai` 가 아니라 코칭 쪽에 두어야 한다. 카테고리 선택 우선순위는
**①이번 주 `COACHING_STARTED` 넛지 → ②예산의 `SPENDING_FOCUS`(`DELIVERY`/`CAFE`;
`FIXED_COST` 는 매핑 없음) → ③월세 제외 직전 4주 최대 지출**이고, **신호가 하나도 없으면
제안하지 않는다**(그때 답변은 4장 1·2번을 쓴다 — 3번은 카드를 약속하는 문구다). ②가 ①을 조용히
이기는 것은 응답만 봐서는 안 보이니 테스트로 고정할 것.

두 가지는 문서가 비워 둔 것을 당시 결정한 것이다: "넛지에서 시작했으면"의 신호는 ERD 7장이
코칭↔넛지 링크를 저장하지 않으므로 **이번 주 `COACHING_STARTED` 넛지로 추론**했고, "직전 4주
주간 평균"은 넛지/ANL-03이 비교에 쓰는 k일 조각이 아니라 **온전한 주**로 끊었다(월요일에
호출하면 하루치를 평균 내 터무니없는 목표가 나온다).

**COACH-04는 `CHALLENGE` 의 유일한 작성자이자 `COMPLETED` 로 가는 유일한 전이다.** 그 두 사실이
명세 COACH-04의 "미확정 제안은 챌린지로 등록하지 않음"(SRS 7.3-3)을 구조적으로 보장한다.
코칭을 끝내는 코드는 **같은 트랜잭션에서 챌린지를 만들어야** 한다 — `CHALLENGE.CREATED_AT` 이
코칭의 종료 시각이므로(ERD 7장) 챌린지 없는 `COMPLETED` 코칭은 그 시각을 잃는다.

- **요청을 저장된 제안과 비교하지 말 것**(ERD 9장 스냅샷). ± 조정은 저장되지 않으므로 요청이
  진실이고, 제안 컬럼은 "AI가 무엇을 권했는지"의 기록으로 남는다
- **409 두 개의 순서: `COACHING_ALREADY_ENDED` 먼저, 그 다음
  `CHALLENGE_ALREADY_IN_PROGRESS`.** 둘이 동시에 참인 경우는 같은 코칭을 두 번 확정할 때(더블
  클릭)뿐이고, 그때는 경로로 지목된 자원 쪽이 더 정확한 답이다. 동시 중복은
  `CHALLENGE.COACHING_ID` 의 UNIQUE가 막는다
- **검증을 둘로 나눌 것.** 필드별 규칙(필수·길이·`@Min(1)`·과거 날짜 금지)은 애노테이션으로 —
  그래야 `details[{field, reason}]` 이 나온다. 조합 규칙(목표가 `goalType` 과 맞는지,
  `endDate ≥ startDate`, 기간 ∈ {7,14,30})은 서비스에서 — 애노테이션으로 만들면 명세에 없는
  `reason` 값을 세 개 발명해야 한다
- 없는 `categoryId` 는 **404**(TX-01 선례)지만 존재하는 **수입** 카테고리는 **400** — 그건
  요청 표의 "지출 카테고리" 규칙이고, CAT-01이 목록을 공개하므로 존재를 숨길 이유도 없다
- `global.validation.NotPastDate` 는 **남아 있다**(`NotFutureDate` 의 쌍둥이). 둘 다
  `KstTime.today()` 로 판단하고 `null` 을 통과시킨다. reason 은 `PAST_DATE` 이고 **이건 명세가
  아니라 우리 관례**다 — 애노테이션 이름을 바꾸면 API 계약이 바뀐다

첫 메시지 생성 포트(`AI_대체_문구.md` 3장)와 COACH-03 답변 포트는 **계약이 달라야 한다**:
첫 메시지 쪽은 명세에 에러가 없고 문구가 미리 씌어 있으니 **절대 던지지 않는다**. 답변 쪽은
실패를 `isFallback: true` 로 드러내야 하고 폴백이 DB를 읽어야 하므로 **던진다**. 넛지 컨텍스트는
nullable 필드 세 개가 아니라 **nullable 레코드 하나**로 받을 것 — 문서의 두 템플릿 묶음이 그
존재 여부로 갈리고, 필드를 쪼개면 "카테고리는 있는데 금액은 null" 이 표현 가능해져
사용자에게 `null원` 이 찍힌다.

### ④ 달성률 계산 (거래 후처리 2번)

| | |
|---|---|
| **만들 것** | `CHALLENGE` 의 실적 세 컬럼을 갱신하는 후처리, 그리고 그 호출을 `TransactionService` 에 다시 끼우기 |
| **남아 있는 것** | 호출이 들어갈 자리를 표시한 주석 3곳 (`TransactionService` 의 `create`/`update`/`delete`) |
| **읽을 곳** | `서버_내부_처리.md` 1장 순서 2번 · 2장 · SRS 7.4-2 |

1차 인수인계 때는 `ChallengePerformance` 인터페이스 + `NoOp` 구현으로 **포트를 남겼지만**,
챌린지 도메인 전체가 넘어가면서 포트가 있을 자리도 없어졌다. 그래서 지금은 **주석만** 남아 있다.
지켜야 할 것:

- **같은 트랜잭션 안에서 동기로**, 그리고 **넛지 판정 바로 앞**. 순서는 `서버_내부_처리.md`
  1장이 정한 것이다
- **전체 재집계 후 덮어쓰기**(= 멱등). 방금 바뀐 거래 한 건을 더하는 방식이면 삭제된 거래가
  합계에 영원히 남는다. TX-05가 수정 전·후를 각각 한 번씩 부르는 구조도 멱등을 전제로 한
  것이라, 누적 방식으로 바꾸면 이중 집계가 된다
- 인자는 **거래의** 카테고리와 날짜다 — 그 조합으로 재계산할 챌린지를 고르고(2장의 세 조건),
  집계 범위는 **고른 챌린지의 `START_DATE ~ END_DATE`** 다. 이 구분이 "수정으로 날짜가 기간
  밖으로 나간" 경우를 처리한다(수정 전 날짜로 부르면 그 거래가 빠진 합계가 된다). 그래서
  **TX-05는 수정 전 날짜도 붙잡아야** 하고, `TransactionService.update` 에 그 자리를 주석으로
  표시해 뒀다
- 금액과 횟수는 **같은 스냅샷에서** 와야 한다 — 원래
  `TransactionRepository.sumCategorySpending` 이 한 행으로 둘을 돌려줬고, 그 메서드와
  projection(`SpendingTotal`)은 **남아 있다**
- 달성률은 `HALF_UP` scale 2 (이 레포의 비율 관례). **어느 실적과 어느 목표를 나누는지는
  `goalType` 이 정한다** — 종료 판정이 보는 짝과 같아야 달성률과 판정이 어긋날 수 없다
- **상태는 절대 건드리지 않는다.** 목표 초과가 자동 실패·취소가 아니고(ERD 9장에 `CANCELED`
  라는 값도 없다), 달성률도 **100에서 깎지 않는다** — 얼마나 초과했는지가 지워진다
- 종료된 챌린지는 **쿼리에서** 걸러낼 것(`IN_PROGRESS` 만). `서버_내부_처리.md` 1장이 종료된
  챌린지를 얼리고, 서비스 쪽 필터는 호출자 하나가 잊으면 끝난다

### ⑤ 챌린지 (CHL-01/02)

| | |
|---|---|
| **만들 것** | `CHALLENGE` 테이블·엔티티, CHL-01/02 |
| **남아 있는 것** | 없음 |
| **읽을 곳** | 명세 CHL-01/02 · ERD 9장 · SRS 7.4 |

- **`CHALLENGE` 에 `USER_ID` 를 두지 말 것**(ERD 9장). 소유자는 `COACHING.USER_ID` 로 도달한다 —
  모든 쿼리가 `ch.coaching.user.id` 로 조인했고, 그래야 "코칭의 주인 ≠ 챌린지의 주인"이 표현
  불가능해진다
- **`COACHING_ID` 는 UNIQUE** — 그게 COACHING 1 : 0..1 CHALLENGE, 즉 한 대화가 두 번 확정할 수
  없다는 제약이다
- 생성은 최종 값을 **인자로 받고 코칭의 제안 컬럼을 읽지 않는다**(ERD 9장이 그 중복을 의도된
  스냅샷이라고 못박았다). 제안을 읽으면 사용자의 ± 조정이 조용히 사라진다
- **판정은 엔티티 안에서, 두 번 돌기를 거부할 것** — ERD 9장의 "늦은 기록은 반영하지 않아요"가
  판정된 챌린지를 얼린다는 뜻이고, 상태 setter를 엔티티 밖에 두면 누구나 녹일 수 있다.
  "목표 이하"가 성공이므로 **같으면 SUCCESS**이고, `COUNT` 목표는 금액이 아무리 작아도 횟수로
  판정한다
- **CHL-02는 종료된 챌린지도 연다** — 상태로 걸러내지 않는다(CHL-03 성장 리포트로 가는 길이다)
- 소유권은 쿼리에(`findByIdAndCoachingUserId`) — 없는 것과 남의 것이 바이트 단위로 같은 404
- **`data` 는 페이지 정보 없는 배열**(명세 CHL-01 예시) — CAT-01과 같은 모양. 쌓이기는 하지만
  한 번에 하나씩 하는 챌린지라 느리게 늘고, 페이징을 넣으려면 명세를 먼저 고쳐야 한다
- **`daysLeft` 는 저장하지 않고 계산한다** — `endDate − 오늘`(`KstTime.today()`)이라 마지막 날은
  0이고 기간 길이가 아니다. **음수는 0으로 깎을 것** — 끝난 챌린지가 "D-34"에 `-34` 를 내보내면
  안 되고, 명세가 그 경우를 다루지 않으며 `status` 가 이미 끝났다고 말한다
- **`coachingId` 는 응답에 넣지 않는다** — 화면이 쓰지 않고, 남의 코칭 id를 추측할 재료가 된다
- 조회 시점에 **다시 집계하지 말 것** — 후처리 2번이 컬럼을 최신으로 유지한다(2장이 갱신 주체를
  못박았다). 두 번째 집계 경로는 같은 숫자가 둘로 갈리는 시작점이다
- 정렬은 **우리 결정**이다: 확정 최신순(`createdAt` desc, `id` desc). `CREATED_AT` 은 확정
  시각이고 변하지 않아서 실적이 갱신돼도 목록이 재배열되지 않고, `id` 가 같은 초의 동률을 깬다
  (없으면 실행마다 순서가 달라진다)
- `?status=` (빈 값)은 "전체"다 — 선택형 enum에서 Spring이 blank를 `null` 로 바꾼다. ANL-01의
  `?yearMonth=` 가 400인 것과 **일부러 다르다**(그쪽은 직접 파싱하는 `String` 이라 blank가 진짜
  오류다)

### ⑥ 성장 리포트 + 챌린지 종료 판정 + DEV-02

| | |
|---|---|
| **만들 것** | `GROWTH_REPORT` 테이블·엔티티, CHL-03, 종료 판정, 00:05 스케줄러, DEV-02, 결과별 피드백 문구 생성 |
| **남아 있는 것** | 없음 |
| **읽을 곳** | 명세 CHL-03 · DEV-02 · ERD 9·10장 · `서버_내부_처리.md` 4장 · 11장 · `AI_대체_문구.md` 7장 |

만들 때 주의할 네 가지:

1. **판정기와 스케줄러는 빈 두 개로 분리할 것.** 루프가 자기 빈의 `@Transactional` 메서드를
   부르면 프록시를 거치지 않아 애노테이션이 조용히 무시되고, 한 건 실패가 그날 전체를
   롤백시킨다. 개별 판정은 `REQUIRES_NEW`.
2. **스케줄러는 조건 기반으로**(`endDate < today AND IN_PROGRESS`) — "마지막 실행 시각"을
   저장하지 않으면 서버가 꺼져 있던 날도 다음 실행에서 따라잡는다. `endDate < today` 라서
   **마지막 날은 아직 판정하지 않는다**(자정까지 기록이 더 들어올 수 있다).
3. **DEV-02는 판정기를 재사용**할 것(4장 마지막 줄). 판정 메서드가 `endDate` 를 보지 않는
   덕분에 아직 진행 중인 챌린지도 끝낼 수 있다 — 날짜 조건은 스케줄러의 쿼리에만 둔다.
   DEV-02에 거래를 더할 때는 리포지토리가 아니라 **TX-01 경로**로 넣어야 후처리 2번이 돌아
   판정이 최신 실적을 본다. 그리고 DEV-02의 서비스는 **`@Transactional` 이 아니어야** 한다
   (판정이 `REQUIRES_NEW` 라 바깥 트랜잭션이 있으면 방금 넣은 거래가 안 보인다).
   시나리오 퍼센트(**SUCCESS 70% · FAILED 112%**)는 시연_데이터 5장 8단계의 예시에서
   역산한 값이다(목표 50,000 · 실적 24,000 → +11,000 = 35,000 / +32,000 = 56,000). 거래를
   **더하는 것만 가능하므로** 이미 목표를 넘긴 챌린지는 SUCCESS로 구제할 수 없고 `COUNT`
   목표는 아예 구제가 안 된다 — 그 경우는 경고만 남기고 실제 기록으로 판정하면 된다.
4. **`BEFORE_AMOUNT`/`BEFORE_COUNT` 가 테이블이 존재하는 이유다.** 나머지 숫자는 이미
   `CHALLENGE` 에 있다. 챌린지 직전 같은 길이 기간(`[startDate − 기간, startDate − 1]`)을
   **판정 시점에 얼려** 두지 않으면, 과거 거래를 수정했을 때 사용자가 이미 본
   "챌린지 전 107,000원"이 조용히 바뀐다.

피드백 문구 생성은 **절대 던지지 않는 계약**으로(ERD 10장: "생성 실패 시 결과별 템플릿"), 그래서
판정에 `try/catch` 가 없고 문구는 **동기로** 만든다 — 스케줄러에 지켜야 할 응답 시간이 없다.
`{gap}` 만 `COUNT` 에서 단위가 바뀌고(7장 각주) `{before}` 는 언제나 금액이다.

CHL-03의 404 **세 가지는 한 조회로 합칠 것** — 없는 챌린지, 남의 챌린지, 진행 중이라 리포트
없음. 구분하면 ID를 훑어 남의 챌린지 존재를 알 수 있고(명세 0장 5)), 프론트는 어느 경우든
"아직 리포트 없음"으로 같게 처리한다. 컨트롤러의 `/{id}/report` 는 **`/{id}` 핸들러 아래**에
둘 것(리터럴 경로가 더 구체적이라 Spring이 먼저 매칭하므로 `report` 가 ID로 해석되지 않는다).

`difference` 는 **부호 있는 값**(`목표 − 실적`, 양수면 목표 아래)으로 내려보냈다. 7장의
`{gap}` 은 절댓값이지만 템플릿이 방향을 말로 쓰므로, 화면은 부호에서 방향을 읽는다. `goalCount`
도 응답에 넣는 쪽으로 정했다 — 명세 예시는 `AMOUNT` 챌린지라 빠져 있지만, `COUNT` 리포트는
그게 없으면 `difference` 를 읽을 수 없다.

### ⑦ ADMIN-01 (KPI)

| | |
|---|---|
| **만들 것** | `GET /admin/kpi` |
| **남아 있는 것** | `AdminSeeder`, `User.admin(...)`, `Role.ADMIN`, `SecurityConfig` 의 `/admin/**` → `hasRole("ADMIN")`, `ApiAccessDeniedHandler` |
| **읽을 곳** | 명세 ADMIN-01 · ERD 13장 |

- **권한 검사를 서비스에 넣지 말 것.** `SecurityConfig` 가 이미 `/admin/**` 를
  `hasRole("ADMIN")` 으로 막고 `ApiAccessDeniedHandler` 가 403 본문을 쓴다. Java에서 역할을
  다시 보면 규칙이 두 곳에 생긴다. **관리자 권한만 URL 패턴 인가이고, 소유권은 절대 아니다**
  (소유권은 404 — 명세 0장 5))
- **KPI 쿼리에는 사용자 범위가 없다**(ERD 13장) — 다른 챌린지 쿼리와 달리 `COACHING` 을 조인
  하지 않는다. 프로젝트 전체 수치다
- `WHERE` 는 **`status in (SUCCESS, FAILED)`**, `status <> IN_PROGRESS` 가 아니다. 지금은 두
  표현이 같지만 상태가 하나 늘면 두 번째 형태에서는 조용히 분모에 들어간다. `sum` 에
  `coalesce` 가 필요하다 — 종료된 챌린지가 없으면 `count = 0` 인데 `sum` 은 `null` 이라
  unboxing에서 NPE가 난다
- **종료된 챌린지가 없으면 `achievementRate: 0.00`, `isAchieved: false`** (명세는 침묵. 2026-11-10
  결정). `null` 은 게이지를 NaN으로 만들고 나눗셈은 0으로 나누기가 된다 — ANL-01의
  `budgetUsageRate` 와 같은 판단이다. `endedChallengeCount: 0` 이 이미 집계할 게 없다고 말하고,
  "데이터가 없어서 달성"은 발표에서 오해를 부른다
- `target`(70.00)은 **서버가 준다** — 프로젝트 KPI이고(ERD 13장), 화면에 박아 두면 API의 값과
  갈라질 수 있다

**`AdminSeeder` 는 남아 있다.** `User.admin(...)` 은 `ADMIN` 을 만드는 유일한 방법이고 그
시더가 유일한 호출자여야 한다 — ERD 1장이 **가입으로** ADMIN을 만드는 것을 금지하므로
`signUp` 은 `Role.USER` 를 하드코딩한다. 시더는 **`@Profile("dev")`** 다: 시연_데이터 1장에
비밀번호가 적혀 있어 운영에 두면 백도어다. 그래서 운영에는 관리자가 없고, 지금은 KPI
엔드포인트도 없으므로 그 계정으로 할 수 있는 일이 아무것도 없다(무해하다).
`AdminSeederTest` 가 계속 돌고 있다.

## 2. 구현 순서 (의존 순서)

```
A. 이상치 탐지 (Z 계산 + 공용 표본 수집)
      ├─> ANL-03
      └─> 넛지 테이블·엔티티
                ├─> 넛지 판정 (후처리 3번)
                │        ├─> NDG-01~03
                │        └─> 후처리 5번 (AI 문구)
                └─> (코칭의 신호 ① · COACH-01 의 nudgeId)

B. 챌린지 테이블·엔티티 (COACHING 이 선행 — FK·소유자 경로)
      ↑
   코칭 테이블·엔티티 ─> COACH-01/02 ─> COACH-03 ─> COACH-04 ─> CHL-01/02
                                                          ├─> 달성률 (후처리 2번)
                                                          └─> 종료 판정 ─> 성장 리포트 + CHL-03
                                                                      └─> DEV-02
                                                                      └─> ADMIN-01

C. Gemini 어댑터 (TX-07 → RCPT-01)   ← A·B 와 독립
```

주의할 선후 관계:

- **A를 먼저.** ANL-03과 넛지 판정이 **같은 계산 함수**를 써야 한다. 뒤집어 넛지부터 만들면
  ANL-03이 두 번째 계산 경로를 갖게 되고, 그 상태로 숫자가 맞으면 아무도 눈치채지 못한다.
- **코칭이 챌린지보다 먼저.** `CHALLENGE` 에 `USER_ID` 가 없어서 `COACHING` 없이는 소유자에
  도달할 수 없다(ERD 9장). 테이블 순서가 곧 작업 순서다.
- **COACH-04가 챌린지의 유일한 작성자**이므로 그게 없으면 CHL-01/02를 실제 데이터로 검증할
  방법이 DEV-01 시드뿐이다.
- **달성률(후처리 2번)이 종료 판정보다 먼저.** 판정은 후처리 2번이 쓴 실적을 읽는다 — 없으면
  전부 0원으로 판정된다.
- **ADMIN-01은 종료 판정 다음.** `status in (SUCCESS, FAILED)` 인 행이 있어야 의미 있는 숫자가
  나온다.
- C는 아무 때나.

## 4. 호출 순서는 아직 코드에 남아 있다

`서버_내부_처리.md` 1장이 정한 후처리 순서 중 **3번의 호출만** `TransactionService` 에 살아 있다
(`create`/`update`/`delete` 세 곳). 2번이 들어갈 자리는 **그 바로 앞에 주석으로** 표시해 뒀다.

- 둘은 **같은 트랜잭션에서 동기로** 돌아야 한다. 이벤트 리스너로 바꾸지 말 것 — 거래 저장과
  후처리가 한 커밋에 묶여야 "저장은 됐는데 진행률/카드만 안 움직인" 상태가 없다
- **순서가 규칙이다**(2번 → 3번)
- `update`(TX-05)는 **수정 전** 카테고리를 변경 적용 **전에** 붙잡아 둔다. 후처리 2번이 돌아오면
  **수정 전 날짜도** 같이 붙잡아야 한다(주석에 적어 뒀다)
- `delete`(TX-06)는 지우기 **전에** 카테고리와 날짜를 붙잡는다 — 지운 뒤에는 얻을 수 없다
- 후처리 5번(AI 문구)만 커밋 후 비동기다

**`AsyncConfig` 를 지우지 말 것.** 지금 `@Async` 소비자가 없어서 지우고 싶어지지만, 이 클래스는
executor를 **이름(`applicationTaskExecutor`)으로 고정**해서 `@EnableScheduling` 과의 충돌을
막고 있다. `TaskScheduler` 도 `TaskExecutor` 라서, 고정하지 않으면 비동기 작업이 스케줄러
풀(기본 크기 1)로 조용히 이주한다. 2026-11-10에 정확히 그렇게 깨진 기록이 있다.

**`spring.task.scheduling` 풀 크기는 1**(Boot 기본)이다. 그래서 두 스케줄러의 cron이 5분
떨어져 있었다 — 00:05가 챌린지 종료, 00:10이 Refresh Token 정리다. 종료 판정을 되살릴 때
**00:10을 비워 둘 것**.

## 5. 먼저 알아야 할 함정

1. **`ErrorCode` 를 건드리지 말 것.** `ErrorCodeTest` 가 enum을 명세 0장 4) 표와 diff 한다 —
   코드를 추가하려면 **명세를 먼저 고쳐야** 빌드가 통과한다. 의도된 장치다. 이 작업에 필요한
   코드(`AI_UNAVAILABLE`, `AI_PARSE_FAILED`, `COACHING_ALREADY_ENDED`,
   `CHALLENGE_ALREADY_IN_PROGRESS`, `NOT_FOUND`, `FORBIDDEN` …)는 전부 이미 있다.

2. **"사용자당 진행 중 챌린지 하나"를 지키는 코드가 지금 아무것도 없다.** ERD 9장에 unique
   index가 없어서 DB 제약이 아니라 COACH-04가 코드로 지키던 불변식이고, 그게 사라졌다.
   되살릴 때 반드시 같이 넣을 것 — 이게 빠지면 DEV-01 시연 흐름(진행 중 0건 상태에서 COACH-04로
   하나 만들기)이 조용히 깨진다.

3. **마이그레이션 도구가 없다.** Flyway/Liquibase 둘 다 없고 스키마는 Hibernate가 추론한다.
   다섯 테이블을 다시 만들 때도 **엔티티가 스키마의 정의**다. 운영 DB(`ddl-auto=update`)에는
   지운 테이블이 **그대로 남아 있을 수 있으니** 컬럼이 ERD와 맞는지 확인할 것 — 테스트는
   `create-drop` 이라 이 차이가 안 보인다.

4. **시간대.** `KstTime.today()` 가 "오늘"의 유일한 정의다. `LocalDate.now()` 를 쓰면 서버 JVM
   기본 시간대에 따라 주·월 경계와 미래 날짜 판정이 서로 어긋난다. 주의 시작은 월요일로 고정
   (`Weeks.FIRST_DAY_OF_WEEK`) — `Locale.getDefault()` 를 쓰면 "이번 주"가 서버 로케일에 달린다.

   예외가 하나 있다: `ExpiredRefreshTokenCleanupJob` 은 **일부러** `LocalDateTime.now()` 를
   쓴다. `EXPIRES_AT` 을 쓴 쪽과 같은 시계를 봐야 하기 때문이다. 둘은 같이 움직이거나 둘 다
   그대로 둬야 한다.

5. **테스트 DB는 모든 스프링 컨텍스트가 공유한다**(`jdbc:h2:mem:was` + `DB_CLOSE_DELAY=-1`).
   그래서 **전역 테이블 내용을 단정하는 테스트를 쓰지 말 것** — 실행 순서에 따라 결과가 바뀐다.
   커밋하는(= `@Transactional` 이 아닌) 테스트를 추가하면 `@AfterEach`/`@AfterAll` 에서 **자기
   행만** 지울 것. `users` 전체를 비우면 dev 컨텍스트의 관리자 계정이 사라져
   `AdminSeederTest` 가 깨진다.

6. **`@Transactional` 테스트로는 후처리 5번을 볼 수 없다.** AFTER_COMMIT 리스너는 테스트
   트랜잭션이 롤백되면 아예 안 돈다. 실제로 커밋하고 SQL로 치우는 방식이거나, `Executor` 빈을
   `SyncTaskExecutor` 로 바꿔 끼우는 방식(통합테스트의 `SynchronousExecution` 중첩 클래스가
   지금도 그렇게 한다)을 쓸 것.

7. **`@WebMvcTest` 는 `controllers = ...` 를 반드시 넘길 것.** 빈 `@WebMvcTest` 는 모든
   `@Controller` 를 스캔해서 슬라이스가 설정하지 않은 리포지토리까지 끌고 오고 컨텍스트가 뜨지
   않는다. `SecurityConfig` 를 `@Import` 하면 `JwtProvider` 와 핸들러들도 같이 넣고 `app.jwt.*`
   를 설정해야 한다 — `SecurityConfigTest` 의 애노테이션 블록을 복사하는 게 빠르다.

8. **쿼리 파라미터 DTO는 `@Valid @ModelAttribute` 레코드로.** 핸들러 파라미터에 제약
   애노테이션을 직접 달면 Spring 7의 메서드 검증이 `HandlerMethodValidationException` 을
   던지고, 전역 핸들러가 그걸 매핑하지 않아 500이 된다. 레코드로 받으면 `BindException` →
   400 `VALIDATION_ERROR` + `details`. ANL-03의 `period`/`baseDate`, CHL-01의 `status` 가 이
   경우다.

9. **남의 리소스는 403이 아니라 404**(명세 0장 5)). 조회 쿼리에 `userId` 를 넣어서 "남의 행"과

   빠뜨리면 존재 여부가 샌다. CHL-03의 404 세 개를 한 쿼리로 합치는 것도 같은 이유다.
   **403은 `/admin/**` 뿐이다**(URL 패턴 인가).

10. **버전.** Java 25 · Spring Boot **4.1.2**(3.x 아님). `spring-boot-starter-webmvc`,

## 6. 구현하면 실패하게 되어 있는 테스트 (= 되살릴 지점)

구현을 넣으면 아래가 깨진다. **버그가 아니라 할 일 목록이다.** 각 위치의 javadoc·주석에 되살릴
단정값을 적어 뒀다.

| 테스트 | 무엇을 되돌리나 |
|---|---|
| `DevSeedApiTest.createsNoNudgeUntilJudgementIsImplemented` | 배달 넛지 한 장 (101,000 / 평균 60,000 / +68.33% / 이번 주 월요일) |
| `DevSeedApiTest.deliverySpikeSeedsTransactions` | `nudgeCreated: true` |
| `DevSeedApiTest` (주석 블록) | 과거 챌린지 4건(C2만 FAILED, 달성률 150.00) · 진행 중 0건 · 챌린지마다 코칭 1 + 메시지 2 · 코칭 20:00 / 챌린지 20:05 백데이트 |
| `DevSeedApiTest.theDemoScreensWorkRightAfterSeeding` | 시연 3단계 NDG-01 호출, 완료 챌린지 목록 4건 |
| `DevProfileOnlyTest.devBeansAreNotRegistered` | `DevChallengeController`/`Service` 빈 부재 단정 |
| `FullApiJourneyIntegrationTest` | ANL-03 ×2 · NDG-01/02/03 · COACH-01~04 · CHL-01/02/03 · DEV-02 · ADMIN-01 단계, `cleanUp` 의 자식-우선 삭제 순서, `@Order` 재부여 |
| `OpenApiDocsTest` | `SPEC_ENDPOINTS` 에 12줄 추가 (목록은 그 javadoc에 그대로 있다) |

**통합테스트는 상태를 필드로 넘긴다.** `@TestInstance(PER_CLASS)` + `@Order` 이고, 각 단계가
**이전 단계의 응답 JSON에서만** 값을 꺼낸다. 단계를 끼워 넣으면 번호를 다시 매겨야 하고, N번째가
실패하면 그 뒤가 전부 실패한다 — 그게 의도된 신호다. 리포지토리를 주입하지 말고, SQL은
`cleanUp()` 에만 쓸 것.

통합테스트의 단정값은 **요일 보정 규칙**(시연 3-5) 덕에 주간 숫자가 요일과 무관하게 같아서 쓸 수
있는 것이다. **월 누적은 경과일에 따라 달라지므로** 월별 단정은 고정값(1일의 급여·월세)과
불변식(`잔액 = 예산 − 총지출`)만 쓴다.

**DEV-01의 시연 데이터는 지금 거래와 예산만 깐다.** 시연_데이터 4장의 과거 코칭·챌린지 4건이
빠졌으므로 CHL-01 목록도 ADMIN-01의 KPI(4건 중 3건 = 75%)도 재현되지 않는다. 되살릴 값은 4장에
그대로 있고, 상태(SUCCESS·FAILED)는 **직접 넣지 말고 판정 메서드에 맡길 것** — 그러면 문서의
결과(C2만 FAILED)가 그대로 나오고, 시드와 판정 규칙이 어긋날 수 없다.

## 9. 작업 규칙 (레포 공통)

- API ID 단위로 작업(예: NDG-01)
- 커밋 전 `./gradlew test` 통과. 항상 `./gradlew` (Gradle 9.8.2 고정)
- 명세와 다르게 구현해야 할 이유가 생기면 **구현 전에 질문**
- 응답은 공통 형식 `{success, data}` / `{success, error}`, 에러 코드는 명세 0장 목록만
- 시간대 KST. 날짜만 있는 필드는 `LocalDate`, 금액은 `int`(원), 비율은 `BigDecimal` scale 2
- enum은 `@Enumerated(EnumType.STRING)`, 테이블 이름은 복수형, 모든 엔티티는 `CREATED_AT`·
  `UPDATED_AT` 공통 상속
- 넛지 판정 · 챌린지 판정 · 예산 복사는 **단위 테스트 필수**, 기대값은 `docs/시연_데이터.md` 6장
- 엔드포인트를 추가하면 `@Tag` + `@Operation(summary)` 를 달 것 — `OpenApiDocsTest` 가 검사한다.
  에러 코드는 `@Operation(description)` 의 `**실패**:` 줄에 쓴다(`@ApiResponse` 는 이 레포의
  `ApiResponse` 와 단순명이 충돌한다)
- `/dev/**` 는 **컨트롤러와 서비스 둘 다** `@Profile("dev")`
